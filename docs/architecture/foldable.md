# Foldable and dual-screen displays

This is the design for issue [#49](https://github.com/nsgo-dev/nsgo/issues/49). Fold and hinge geometry belongs in the shared driver model, reported with each surface's size, so an app can reason about the usable regions of a surface without importing Android or vendor types. Android and iOS 27.1 report it; it is still to be checked on a foldable device and a fold simulator ([roadmap](../roadmap.md#foldable-displays)).

## Environment model

`driver.Geometry` (`internal/driver/fold.go`), which `core.Env.Geometry` returns, is a list of usable regions plus the obstructions between them. Each `Region` has a frame in surface points, a safe area, and a reserved rectangle that the app must not place content across, empty when there is none. A fold or hinge is an `Obstruction`: a frame, an orientation (`Horizontal`, else vertical) and three properties that vary independently, as they do in both platforms' models. `Occluding` says the pixels under it are not shown or touched (Android's `occlusionType` `FULL`, UIKit's occlusion region kind). `Separating` says the regions on either side read as logically apart (Android's `isSeparating`, UIKit's division region kind). `State` is the hinge's `HingeUnknown`, `HingeClosed`, `HingeHalfOpen` or `HingeOpen`, open as far as the device goes, which Android calls flat (Android's `FLAT` and `HALF_OPENED`, `UIHingeStatus`), with an `Angle` in radians where the platform reports one, as `HasAngle` says. A hinge between two panels lying open is occluding, separating and open at once; a flexible screen half folded is separating and half open but not occluding; the same screen opened flat is neither. The model describes geometry; it does not choose a two-pane layout.

`driver.Divide` derives the regions from the obstructions at a size: a separating obstruction that crosses the surface from edge to edge splits it, its frame belonging to neither side; one that does not divide the surface, such as a fold that occludes without separating, reserves its frame in the regions it lies in. Frames are clipped to the surface, and those outside it or without length are left out. Non-foldable targets report one region and no obstructions, which the zero `Geometry` stands for. Neither platform gives an order, so regions and obstructions are ordered by frame position: top to bottom, then left to right. Frames are in the same coordinate space as `Tree.Resize`, measured at the surface size the geometry travels with ([updates](#updates)). Core fills each region's safe area with the part of the surface's `SafeArea` that falls in it.

Because the properties are separate, an app can tell an occluding hinge, where pixels cannot be shown, from a separating fold, where both sides remain visible but a continuous layout is undesirable, and a backend never has to drop one property to report another. System bars and cutouts are not obstructions: they continue to use `SafeArea`. Apps can therefore choose a split, a spanning layout with a gap, or a single-region layout explicitly.

## Layers

`internal/driver` owns the serializable geometry and the state enum. `core.Env` exposes the value as a signal that changes only when the geometry or the safe area in its regions does, and keeps its existing device-neutral behavior. `ui` and `base` do not switch forms merely because a device has a fold; an app or component author reads the regions and chooses its own navigation and tab-bar placement.

## Platforms

The backend translates platform geometry into the shared model. Vendor-specific labels and hinge sensors remain backend metadata unless they affect usable geometry. Targets without a system concept of a fold, every one but Android and iOS, report the one-region form, as do desktops' multi-display arrangements.

Android has no fold API in `android.jar`, which is all the Java runtime compiles against (`internal/platform/android/runtime/build.sh`): `FoldingFeature` and `WindowLayoutInfo` come from Jetpack's `androidx.window:window`, a Kotlin library that pulls in the Kotlin standard library, coroutines and `androidx.core`. Bundling it would put those classes into the committed `classes.dex` and into the `classes.jar` that `nsgo build -embed` hosts dex themselves, where a host app that already uses `androidx.window` gets duplicate classes. The runtime takes the route Jetpack itself sits on instead: the device's `androidx.window.extensions` library, which the OEM ships, reached by reflection (`Folds.java`): `WindowExtensionsProvider.getWindowExtensions()`, its `WindowLayoutComponent` and `addWindowLayoutInfoListener`, with the activity and a `java.util.function.Consumer` at vendor API level 1, and with a context and the library's own `Consumer` from level 2; its `FoldingFeature`s give bounds in the window, a type (`TYPE_FOLD` or `TYPE_HINGE`) and a state (`STATE_FLAT` or `STATE_HALF_OPENED`). The `nsgo` tool declares the library, with `<uses-library android:name="androidx.window.extensions" android:required="false"/>`, in the generated APK's or App Bundle's manifest and the `-embed` AAR's only for an app that reads `core.Env.Geometry`: one whose executable keeps the method's name, which the linker leaves out where nothing reaches it, and one of whose packages outside NSGo's internal ones selects a `Geometry` that is not an imported package's, since reflection by names that are not constants, as `tsx`'s, keeps every exported method; another app's class loader never loads it. The views of an activity listen while they are in a window, from API 30, through one listener, as the library takes one for each context and ignores another. The Go side (`internal/platform/android/fold.go`) derives the properties as Jetpack's `HardwareFoldingFeature` does: occluding when the bounds have area, separating for a hinge or a half-open fold, horizontal when wider than tall; and keeps only a feature of a known type and state that crosses the view from edge to edge without covering it. Where the library or the component is missing, the runtime reports the one-region form. A report goes out with the view's size in `START`, which the first commit is laid out with, and in `RESIZE`, its frames clipped to the view in pixels, so an edge the view cuts a feature at is the view's edge exactly. A report of its own is a resize to the same size at the view's next layout, as the library reports when a configuration is applied, before the traversal that gives the view the window's new size; it includes display changes while an activity is resized.

iOS has the concept from 27.1, in the SDK's UIKit headers: `-[UIView reservedRegionsOfKind:]` returns `UIViewReservedRegion`s of `occlusionRegionKind` or `divisionRegionKind`, each with a `frame` in the view's coordinates that includes its `margins` for interactive content, and `isActive`; `UIHingeInteraction` reports a `UIHinge` whose `status` is `Unknown`, `Closed`, `PartiallyOpen` or `FullyOpen`, with its `angle`. The backend (`internal/platform/ios/hinge.go`, mapped in `fold.go`) reads the surface view's active regions in its `layoutSubviews`, where it reports the size now, and as the engine starts, so they go with the resize and the first commit: an occlusion region becomes an occluding obstruction, a division region a separating one, and regions of both kinds at one frame one obstruction with both properties. Each frame keeps its margins, so no content is placed in them. The hinge interaction's updates set every obstruction's state and angle and lay the view out again, a change of state alone being a resize to the same size. An occlusion region along an edge of the view that divides nothing is left to the safe area, as the system's bars are, so a vertical bar never becomes an obstruction. Both mappings, one region of each kind at the same frame for a hinge and the vertical bar through the safe area only, are what a fold simulator or device is still to confirm. The trait collection's `verticalBarEdge` (`UIVerticalBarEdge`: unspecified, leading or trailing) is the edge the system chose for a vertical bar; it is not geometry, so it goes into `driver.Environment.VerticalBarEdge` and arrives through `SetEnvironment` from `traitCollectionDidChange:`, which `core.Env.VerticalBarEdge` reads. The backend reaches all of them through purego's Objective-C runtime as it does the rest of UIKit, checking the classes and `respondsToSelector:` first, so earlier systems report the one-region form.

The rest of #49 is packaging: the generated `Info.plist` hardcodes `UIRequiresFullScreen` true and `UIApplicationSupportsMultipleScenes` false (`cmd/nsgo/ios.go`), and `apple.info` takes strings only, so neither can be overridden; the [roadmap](../roadmap.md#foldable-displays) records it.

## Updates

The geometry and the surface size change together, so they travel together. `driver.Environment` keeps the size out (`Tree.Resize` reports it), and the engine merges a queued resize into the slot of an older one, which can move it ahead of an environment pushed before it; geometry sent through `SetEnvironment` could therefore be applied at a size it was not measured at. The geometry is instead part of the resize: `Engine.Resize` and `ResizeAndWait` take it with the size, `engine.Options` with the size the first commit is laid out at, and a change of state at the same size, such as a fold half closing, is a resize to the same size with a new geometry. Merging queued resizes keeps the newest size and geometry as one, and `Tree.Resize` sets `Env().Window` and the geometry in one batch, applying a new geometry at a size it already has, so what reads either sees both new.

When the backend reports a size its latest platform observation was not measured at, it sends the one-region form for the new size until the platform reports for it, rather than frames in the previous coordinate space: Android sends no features while the window's bounds differ from those of the latest report, and iOS reads its regions at the size it reports. Safe areas and the rest of the environment keep arriving through `SetEnvironment`. A surface that detaches keeps its last geometry but reports no new state until it attaches again: the Android view stops listening when it leaves its window and resends the latest report when it attaches again.

## Layout and input

The core's layout remains continuous in the surface's coordinate space. A reserved rectangle clips or rejects content only when the app's own layout asks it to; core does not insert a gap, duplicate a navigation bar or move a tab bar implicitly. `SafeArea` continues to protect system bars, while the reserved regions are available for an app's own constraints and hit testing.

Pointer and touch coordinates remain surface coordinates. The backend does not remap a touch from one region to another. An app can use a region's frame to decide which pane owns a press, and the core's existing hit testing then follows the resulting tree.

## Verification

These checks exist:

- headless `core` tests (`core/fold_test.go`) cover one-region defaults, the size and geometry changing in one batch, region ordering, reserved and occluding obstructions, a surface that keeps its geometry while nothing reports to it, signals that change only when geometry changes, and two explicit panes an app places on either side of a separating obstruction without any implicit device-specific behavior from core or base;
- `internal/engine` tests cover queued resizes merging with their geometry, including a resize merged ahead of an environment pushed before it;
- `internal/driver` tests cover serialization, empty lists, state transitions and frames outside the surface; no backend gives the shared model pixels, as Android's runtime converts them to points as it does every size;
- iOS tests use recorded reserved regions and hinge updates for an open, a half-open and a closed hinge, rotation and a vertical bar on either edge, and an older system without the selectors;
- Android tests use recorded WindowManager observations for an open fold, a half-open fold, an open hinge between two panels (occluding and separating together), rotation and multi-window states, and the tool's tests check that only an app reading its geometry declares the library.

Still to come is that check on a foldable device and a fold simulator, with the gallery page the [roadmap](../roadmap.md#foldable-displays) names.

An edge-adaptable tab bar, `mobile.TabBar` taking a leading or trailing edge where today it has only the system's bottom form (`core/tabbar.go`), follows as a separate [roadmap](../roadmap.md#foldable-displays) item.

## Decisions

The user confirmed the answers this design proposed on 2026-11-15:

1. The public value is a list of usable regions plus obstructions, not a higher-level fold posture with derived regions.
2. Reserved regions are only geometry: core offers no layout constraint that avoids them.
3. The hinge metadata exposed across Android vendors and iOS is the state, `Unknown`, `Closed`, `HalfOpen` or `Open`, and the angle where the platform reports one.
4. The first release covers Android and iOS 27.1 alone; desktops' multi-display arrangements report the one-region form.
5. The adaptive tab bar is a change to the existing component, `mobile.TabBar` taking a leading or trailing edge, after the environment model.
6. Android reaches folds through the device's `androidx.window.extensions` by reflection, bundling none of `androidx.window` and its Kotlin dependencies.
