# Hosted views

`WebView`, `Video` and `Native` host a platform view inside a view: the platform's web view and player, or one the app registered. Each follows NSH's design and behavior on every target; NSGo changes only the API's shape to Go's. Read this before changing these elements or a backend's host for them.

## Shared design

- The control fills a `KindWeb`, `KindVideo` or `KindNative` view, which keeps the decoration, frame and accessibility.
- One config item carries the whole state: `ItemWeb` with `WebConfig`, `ItemVideo` with `VideoConfig`; `ItemNative` carries a component's changed props.
- Commands ride their own items: `ItemWebCommand` for `Ref`'s history, scripts and messages, `ItemVideoSeek` for `Ref.Seek`, `ItemNativeCommand` for `Ref.Command`.
- Core resolves defaults before sending, so platforms see final values: a video's volume, rate, progress interval and resize mode (Contain).
- Platforms report an event only when the view's `EventMask` has it.
- NSGo keeps Go's zero values as defaults: `NoScroll` and `NoJavaScript` invert NSH's `scrollable` and `javaScriptEnabled`, and `window.nsgo` replaces `window.nsh`.
- Restricted web views check page navigations against `WebHosts` and `AccessWebSchemes` on the native backends; the browser cannot enforce these inside an iframe (`core/access.go`).

## Web views

- A refused page-made `about:` navigation on Linux reports no load start, load or navigation state; its refusal and the previous page's restoration still report normally. WebKitGTK's URI at load start may still name the previous page, so a refused `about:` action holds the next page-made start until its top-level commit accepts or refuses it. A frame's `about:` action can also hold a start, which an allowed commit releases before the load finishes; the app's own HTML loads report their start as usual.
- Every page starts with `WebBridge`, defining `window.nsgo.postMessage(data)`, which reaches `OnMessage` as a string and `OnMessageFrom` with the page's origin. `PostMessage` dispatches a `MessageEvent` on the page's window.
- A message reaches the app only from the page's top frame and only from an origin `MessageOrigins` allows, by default the source's: `driver.WebSource.Origin`, Src's, BaseURL's for HTML, `"null"` for HTML without one, which a page the view navigates to on another origin, a redirect included, does not share. Core checks this in one place (`webNode.allows`) on `EventMessage`'s `Origin`, `URL` and `MainFrame`, which every backend fills, and logs a view's first refusal. Frames never reach the app, so that every platform takes the same messages: Android and Linux tell no caller for a frame's post, and Windows only through `CoreWebView2Frame`, which the host does not follow, so a frame relays through the page with `window.parent.postMessage`, whose event the browser gives the frame's origin. Origins are written as `driver.WebOrigin` does: scheme://host, the port only when not the scheme's own, `file://` for every file, `"null"` for an opaque one (about:blank, data:, blob:null). As every page without an origin of its own has `"null"`, a `"null"` message, allowed by default or listed, reaches the app only from the source's page (`driver.WebSource.Shows`): about:blank for HTML without a base URL, which every backend loads it at (the web's srcdoc, about:srcdoc), and the source's URL otherwise. So a data: or blob: page a frame sends the view to after a user's tap, which Android's WebView loads and WebKit loads for a user's action, does not post as HTML without a base URL; Chromium refuses a page's own top-frame navigations to data: URLs on Windows (`BlockedSchemeNavigationThrottle`), so there a data: page of such HTML is the one `NavigateToString` loaded, reported at about:blank. `"*"` takes every page. A frame can still send the view to an empty about:blank, which posts nothing of its own.
- Each backend tells the top frame and its origin its own way. Apple reads `WKScriptMessage.frameInfo`: `isMainFrame`, and the security origin, or the frame's URL for a document whose security origin is opaque, such as a sandboxed one. Windows hears only the top document through `CoreWebView2.WebMessageReceived` and reads its `Source`. Linux's WebKitGTK reports neither, and gives every frame the message handler, so its bridge, a top-frame user script, prefixes a token of the view's own, which it keeps in a closure with the handler's `postMessage` bound before page scripts run; the page is the view's URI as its load commits (`WEBKIT_LOAD_COMMITTED`), so a page the view only started to load does not take the messages of the one still shown, though a message still in flight as the next page commits takes the new page's. Android gives every frame its JavaScript interface and tells no caller, and `WebViewCompat.addWebMessageListener`, which would, is androidx's, which the runtime does without: `WebNode` makes a token for each page as it starts, runs the bridge holding it with `evaluateJavascript`, which reaches only the top frame, and takes only messages carrying the current page's token, reporting the URL the view showed as it handed it out, so a frame or a later page posting to the interface itself is dropped. android.webkit reports a page's start once it commits, and `evaluateJavascript` reaches the page committed last, so the view gives the bridge only while it shows the committed URL (for HTML, whose commit is a data: URL, its history URL); showing another, it has committed a later page, whose own start follows, or is loading one the app asked for, whose URL the page still shown would otherwise report. A page that starts again, such as one restored from the back-forward cache, gets a bridge with the new token in place of its old one. HTML with a BaseURL takes it as its history URL there, so the view shows the page at the base URL, as other platforms do, rather than about:blank. The web hands the srcdoc page's port to the app only from the frame's own window and with the page's token, and drops it as that page leaves, for a link or a script setting `location`, which its bridge says on `pagehide`, reporting a load start; a page it went to has no bridge, so `InjectJavaScript` and history steps there are dropped with a warning until the source shows again, and those sent while the source's page loads wait for its port.
- `Ref.Evaluate` answers with a script's result as JSON, or its error, through that bridge rather than each platform's evaluation callback, so every backend with web views answers alike, Android's with no runtime rebuilt: `WebEvaluateScript` runs the script as an expression, awaits a promise, and posts the answer after a marker with a random key, which the core takes, ahead of the origin check, for the `Evaluate` waiting on it and never hands to `OnMessage`. A page leaving (`EventLoadStart`, reported while one waits) ends those waiting with an error. On the web, which bridges only an HTML source's page, an `Evaluate` with no such page to come, a URL's or one the page went to, ends with an error at once; elsewhere a page whose bridge is gone never answers.
- A page loads again when the source, an injected script or its request headers change. `Ref.Load` loads a `WebSource` as a new source would, even one equal to the source, through the same access check, which sends nothing for a refused one, and with the view's `Headers` (`driver.WebLoad`, carrying the source in `Data`). It navigates the view as a link does: each backend loads it with the load the source uses, keeping the configured source, which the next change of the source, the scripts or the headers loads again and whose origin messages come from by default. Other settings apply to the live view.
- `Ref.Reload`, `GoBack` and `GoForward` keep an app-owned page's exemption from `AccessWebSchemes`. Apple and Linux retain native history objects for app-created entries, releasing those the browser drops; Windows records CDP's native entry IDs and selects the checked ID for history commands, with `NavigationStarting` also checking its native reload/history kind. Matching a source URL alone never grants a page-created navigation, and a history command's grant holds only for the native back-forward navigation to the entry it chose: a step within one document, such as back to the entry before a `pushState`, starts no navigation, so the page's next navigation of another kind or to another URL drops the grant rather than taking it (WebKit's navigation type on Apple and Linux, `NavigationKind` on Windows). WebKit reloads string HTML as a blank page, so the host replays its bytes; initial HTML that WebKit omitted from history is kept before the first native entry, with `CanGoBack` and `CanGoForward` reflecting it. Apple also exempts a page's own reload of an app-created entry, which can only load the current entry again; a page's own back-forward step, whose target entry WebKit does not report, is held to the schemes on every backend but Android, and Linux, whose WebKitGTK does not say which frame an action is, grants nothing from a navigation action beyond the host command's own. Android already leaves reload/history out of `shouldOverrideUrlLoading`; the web keeps its iframe's behavior and cannot enforce page scheme restrictions.
- `WebView.PinchZoom` lets a pinch magnify the page, off by default: macOS sets `WKWebView`'s `allowsMagnification`; Windows sets WebView2's `IsPinchZoomEnabled` for touch screens and `IsZoomControlEnabled`, as a precision touchpad's pinch reaches a window as Ctrl with the wheel, which also takes Ctrl with + and - away; Android sets `WebSettings`' built-in zoom, its buttons hidden. iOS zooms as the page's viewport says, and WebKitGTK and the browser have no switch, keeping their own handling.
- `WebView.Headers` adds fields to the initial URL request on Apple, Windows, Linux and Android; HTML sources and the web backend do not apply them yet.
- On Apple, a `file:` source uses `WKWebView`'s file loader and grants the page read access to its containing directory; links to files outside that directory are refused, as they are for HTML whose base URL is a `file:` one, outside the base's directory. A page from any other source leaves `file:` links to WebKit unless the view is restricted, which refuses them.
- `WebView.Incognito` uses WebKit's non-persistent data store on Apple, an ephemeral WebKitGTK network session of the view's own on Linux, released with the view and WebView2's in-private controller profile on Windows. `android.webkit` keeps one cookie store and one set of website data per app with no per-view switch, so an incognito view on Android loads with `LOAD_NO_CACHE`, DOM storage (`localStorage`, `sessionStorage`) off and `setSaveFormData(false)`, which Android 8 and later ignore for autofill, while its cookies, IndexedDB and HTTP authentication stay shared with the app's other web views; the web backend has no per-frame storage switch.
- `Scope.SetWebCookies` writes cookies, HttpOnly ones included, to the persistent store every web view of the app shares, as `ItemWebCookies` carrying a `WebCookiesRequest`, answered by `EventWebCookies`; core refuses a cookie no platform takes (a missing name or domain, SameSite None without Secure, a `__Secure-` or `__Host-` name without its prefix's attributes) before any reaches the platform, and holds code an Access holds to `AccessWebView` with `AccessCookies` for each cookie's URL, which no TSX capability grants. Apple sets each `NSHTTPCookie` (HttpOnly through CFNetwork's `HttpOnly` key, which Foundation exports no constant for) in `WKWebsiteDataStore.defaultDataStore`'s `httpCookieStore`; Linux adds a `SoupCookie` through `webkit_cookie_manager_add_cookie` on the app's network session, which needs no web view either; Android sets each cookie's `Set-Cookie` value on a URL it goes to in `CookieManager` and flushes it, through the runtime's `msgCookies` and `msgCookiesSet` rather than the batch, and as Android has one cookie store per app, Incognito views there see them too. WebView2 reaches a profile's cookies only through a web view (`ICoreWebView2_2::get_CookieManager`), so Windows uses a web view of the window showing pages of the app's profile, and while there is none a hidden one it makes in the profile's environment, starting it with the schemes `ServeScheme` serves to the calling scope, as a first web view would; the hidden one closes once a web view of the profile shows pages, since WebView2's processes, and the session cookies, end with the profile's last web view. `AddOrUpdateCookie` applies after it returns, so Windows answers once `GetCookies` lists the cookies, failing after five seconds. The web, tvOS, watchOS and mini programs answer unavailable (`driver.NoWebCookieStore`). Listing and clearing the store is [#112](https://github.com/nsgo-dev/nsgo/issues/112).
- `Env.HasWebView` reports whether the target provides a web view host; it is false on tvOS, whose UIKit target has no WebKit host, and true on the other targets that expose `WebView`.
- `Scope.ServeScheme` registers app-owned URL schemes for web views under that scope, the nearest scope's handler answering, while other subtrees and windows neither load nor serve them; it refuses those web views handle themselves, such as `ws` or `javascript`, which would end the app on Apple. Apple uses `WKURLSchemeHandler`, Windows answers WebView2 resource requests, and Linux registers a WebKitGTK URI scheme once on the shared web context and answers each request from the handlers of the view whose page made it, failing it when that view serves no such scheme; the handler returns bytes and the native host infers their content type. Schemes are read when a native view is first made. WebView2 takes its schemes only as its environment starts, with the batch that makes a profile's first web view: a scheme served after that does not load on Windows, which the log says once. Android and the web backend do not provide this bridge yet.
- Load start and load each come with a navigation state change, carrying `WebNavigation`. Errors arrive as `*WebError` with the failing URL and, on Apple, Linux and Windows, the platform's `Domain` and `Code` (`driver.WebFailure` in the event's `Data`); access refusals and Android's errors leave both empty. A load cut short, stopped or replaced by another (`NSURLErrorCancelled` and `WebKitErrorFrameLoadInterruptedByPolicyChange` on Apple, their WebKitGTK equivalents, WebView2's `OPERATION_CANCELED`, and on Windows the `CONNECTION_ABORTED` WebView2 ends a navigation with when it is stopped, replaced or turned into a download), is no error: Windows drops the failure of a navigation that is not the last one started (`NavigationId`) or that the app stopped or replaced, and holds a `CONNECTION_ABORTED` for half a second, dropping it when a download or another navigation starts, as WebView2 reports those only after the failure; Windows reports the URL that failed, which never committed, rather than the page still shown.
- A web view with `OnDownload` saves what its pages download, as NSH's macOS one does: core sends `WebConfig.DownloadDir`, the app's data directory's `downloads`, and Apple's host turns a main frame's response WebKit cannot show or marked an attachment, and a link asking for a download, into a `WKDownload`; Linux's WebKitGTK host handles its `download-started` signal; Windows' WebView2 host handles `DownloadStarting`; and Android's WebView host handles `DownloadListener`, fetching an http(s) download again with the page's cookies, user agent and Referer and, on the source's origin, its `Headers`, decoding a `data:` URL itself and having the page read a `blob:` URL, which needs the page's JavaScript and holds the whole file in memory, with the `Blob` kept from the link's click so a URL the page revokes right after clicking it still saves (an object URL made before the host's script runs as the page starts, or in a frame, is fetched instead and fails once revoked), with the name a link's `download` attribute gives. These hosts save to `<id>/<file name>` under that directory and report their start, end and bytes or failure; a view that closes cancels the downloads it was saving on Linux and Windows ([roadmap](../roadmap.md#finish-the-existing-platforms)).
- `WebView.Media` lets the pages capture the microphone, the camera or both through `getUserMedia`, as NSH's `webview.media` capability does; TSX's `media` prop sets it, held to a package's `webview` capability's `media` (`AccessMedia`). Each host answers its web view's request from it without the engine's own prompt, so only the system asks the user for each device, and refuses what it leaves out, a request for both needing both: Apple's handler is also the `WKUIDelegate` (`requestMediaCapturePermissionForOrigin:`, macOS 12 and iOS 15), refusing too where the Info.plist lacks the device's usage description, as the system would end the app; Windows handles WebView2's `PermissionRequested` for its microphone and camera kinds, keeping each answer out of the profile every view of the app shares (`SavesInProfile`), and leaves other kinds to WebView2; Linux turns WebKitGTK's `enable-media-stream` on only with a device and answers `permission-request`'s user media requests, refusing screens; Android's `WebChromeClient.onPermissionRequest` asks for `RECORD_AUDIO` and `CAMERA` through the activity first where the app holds neither, as `NsgoView.permissionResult` hears; and the web sets the frame's `allow`, which takes effect from its next page. An app declares the devices in its package: `apple.info`'s usage descriptions, which also claim them under the hardened runtime, and `android.permissions`.
- `Ref.SendInput` gives the page a click, typed text or a key as the user's own: macOS hands the `WKWebView` AppKit events, with each character's US key, so the page's events are trusted (`isTrusted`) and carry user activation, which `InjectJavaScript` cannot do. It takes the keyboard focus first. `Env.CanSendInput` reports this capability; other targets drop it, as NSH's do. TSX apps will need the `webview` capability's `input` for it ([roadmap](../roadmap.md#tsx-and-dynamic-delivery)).

| Target | Host |
| --- | --- |
| Apple | One `WKWebView` host in `internal/platform/apple`; URL loads use `Headers`, `Incognito` selects `WKWebsiteDataStore`'s non-persistent store, `ServeScheme` uses `WKURLSchemeHandler`, `PinchZoom` calls `allowsMagnification` on macOS, and `NoJavaScript` sets the live configuration's webpage preferences, which apply from the next page |
| Windows | A WebView2 composition controller in a DirectComposition visual, between layers of what is drawn after it; URL loads use `Headers` (`NavigateWithWebResourceRequest`), `Incognito` uses WebView2's per-controller in-private profile options, `PinchZoom` sets `ICoreWebView2Settings5::IsPinchZoomEnabled` and `ICoreWebView2Settings::IsZoomControlEnabled`, `ServeScheme` registers secure schemes with an authority and no other allowed origins on the environment (`ICoreWebView2EnvironmentOptions4`) and answers their resource requests, and the backend hit-tests and forwards input. The Evergreen runtime is found in the registry and its DLL called as WebView2's loader would, so nothing ships with the app |
| Linux | WebKitGTK 6.0 hosted in the view's widget, mapped once the view has a size, with URL loads using `Headers`, app-owned schemes registered on the shared web context, website data per app ID in a network session that lives as long as the process (or an ephemeral session of the view's own for `Incognito`) and NSH's history keys and mouse buttons; WebKitGTK has no pinch enable switch, so `PinchZoom` keeps its native behavior |
| Android | `android.webkit.WebView` with a JavaScript interface under the bridge; URL loads use `Headers`, `PinchZoom` turns on the built-in zoom, `Incognito` disables cache, form saving and DOM storage, and the bridge and scripts meant for the document's start run when the page starts, as android.webkit has no earlier hook |
| Web | An `<iframe>`. HTML loads as `srcdoc` in a sandbox with an origin of its own and hands the app the bridge's `MessageChannel` port, its messages reporting the source's origin; a URL gets only `PostMessage` and load events, as the browser hides the page |

## Videos

- A source is a URL, a file path or an `asset:` path resolved against the app's resources.
- `EventLoad` carries the duration and the picture's size in points; `EventProgress` comes every `ProgressInterval` while playing.
- `EventEnd` follows the platform: AVFoundation and Android report every end, then a repeating video starts over; a looping Media Foundation engine, `<video>` or GTK stream never ends.
- A non-repeating video stays at its end through unrelated configuration changes. Changing `Paused` to true and then false replays it from the beginning; seeking before the end resumes there when `Paused` is false, and leaves it paused otherwise. Opening another source starts from that source's beginning.
- `Controls` shows the platform's controls. Windows has none, so it draws NSH's bar.
- `Paused` applies when it changes and when a source opens. Between changes the platform may pause or play the video itself, and the player keeps that state until `Paused` changes; each is reported once, `OnPause` with a `VideoPauseReason` and `OnPlay`, sharing the driver's answer kinds `EventImageInfo` and `EventMenuClosed`, as an `EventMask` has no room left. The built-in controls (`VideoPauseControls`) report on Apple and Android, Control Center and the PiP window on iOS; an interruption (`VideoPauseInterruption`: a call, Siri, another app taking the audio session, the app going to the background) on iOS and, for a video with an `AudioSession`, which holds the audio focus, on Android; and a lost output such as unplugged headphones (`VideoPauseRouteLost`) on both, for a video that is not `Muted`, which has nothing to stop. When an interruption ends and the system lets it, iOS's `AVAudioSessionInterruptionOptionShouldResume` or Android's focus coming back, a video still paused by it plays on and reports `OnPlay`; a permanent loss of the focus and a lost output leave it paused. A play the app does not make keeps its `Rate`: Android sets it on the player, Apple makes it the player's `defaultRate` (macOS 13, iOS 16), at which the controls and the PiP window play. An app that shows its own play state follows them in `Paused`, which takes the video back. `apple/videoplay.go` and `VideoNode.java` keep who holds the play state; Windows', GTK's and the browser's controls play and pause without telling the app yet ([roadmap](../roadmap.md)).
- `AudioSession` is NSH's `audioSession`. On iOS, while a video with one plays, the shared `AVAudioSession` is the playback category in the spoken-audio mode (mixing with others for `AudioSessionMixWithOthers`), and goes back to what it was, deactivated to let other apps play, once none plays (`apple/audiosession_ios.go`); `AudioSessionFunc` (TSX's `audioSession`) changes it as the video plays, and iOS holds the new session before letting the old go, so playback goes on without a gap. On Android the sound is speech, and a playback video holds `AUDIOFOCUS_GAIN_TRANSIENT` while it plays, pausing for another app's focus as above; a change opens the source again. The desktops and the web ignore it.

| Target | Player |
| --- | --- |
| Apple | `AVPlayer` in an `AVPlayerLayer`, or `AVPlayerView` and `AVPlayerViewController` with controls; AVFoundation and AVKit load on the first video |
| Windows | Media Foundation's media engine in frame-server mode, drawing each frame as a Direct2D bitmap |
| Linux | `GtkMediaFile` (GStreamer) in a `GtkPicture` hosted in the view's widget, or a `GtkVideo` with controls; GTK streams have no playback rate |
| Android | `MediaPlayer` on a `TextureView`, with a `MediaController` for controls |
| Web | A `<video>` element |

## Native components

An app registers its own platform views by name, as NSH's embedding apps do (`nsh/docs/dev/embedding.md`): `nsgo.Component(name, factory)` hands `nsgo.Run`'s or `nsgo.NewView`'s backend a `core.NativeComponents` table, so a registry belongs to one surface, never to the process. An iOS or Android app embedding NSGo registers its own Swift or Java components with each view, which take the names Go's table lacks ([embedding](embedding.md)).

- `Native` names the component; its `Props` cross only when they change, a removed one as nil, and `Ref.Command` reaches the component's `Command`.
- The first `ItemNative` makes the component with a `NativeContext`, whose `Emit` reaches `OnEvent` and whose `SetSize` gives the element a natural size, as an image's; a width of 0 asks for its height alone, as a bar as wide as it is placed.
- A prop whose value is an `AnimatedNode` is bound rather than sent, as NSH 0.3.0's are: `NativeConfig.Bindings` names each bound prop's node and whether it outputs a color, and the backend's `Animator` (`BindNative`, `ChangedNatives`) hands the component each value that changed on the frame clock, through `driver.AnimatedPropSetter` or else `SetProp` with a `float64` or a `Color`. A plain value replacing a node is sent; a removed prop is sent as nil. Android binds them in Java as a canvas's arguments are and calls the view's setters, or a registered `NsgoComponent`'s `setAnimatedNumber` and `setAnimatedColor`, never an `AndroidPropMapper`; iOS hosts' components take the optional `setAnimatedNumber:value:` and `setAnimatedColor:argb:`.
- macOS and iOS register `driver.SwitchComponent` themselves, for `core.SystemSwitch`: NSSwitch and UISwitch, showing the user's choice at once and measuring themselves. Its parent centers it rather than stretching it, as a native view with a natural size keeps its aspect when stretched.
- iOS and Android register `driver.TabBarComponent` themselves, for `mobile.TabBar`; Android's measures itself 80 points tall plus the system navigation bar it reaches under.
- Factories run on the main thread and may return nil; an unknown name leaves an empty box and is logged once.
- Registering differs per platform only in what `View` returns, so an app registers a target's components in files built for it, as the gallery's `components_*.go` do.

| Target | `View` returns | Hosted as |
| --- | --- | --- |
| Apple | An `NSView` or `UIView` | A subview resizing with the view; on iOS placed at each frame, as views such as `UITabBar` size themselves |
| Windows | A window handle | A child window following its view after every frame, clipped with a window region to what its clipping ancestors leave visible, above what NSGo draws, as NSH's `NativeComponent::window` |
| Linux | A `GtkWidget` pointer | A widget hosted in the view's widget, as web views and videos are |
| Web | A DOM element (`js.Value`) | A child element filling the view |
| Android | The name of a `View` class | Built by reflection in the Java runtime, props set through its one-argument `set` methods and commands through its methods; the Go process cannot make views |

On Android the runtime also installs a listener on each `setOn…Listener` method the view's own class declares and reports its callbacks as events named after them, their arguments as a JSON array. A component may implement `android.PropMapper` to turn a prop into ordered setter calls, and `android.EventMapper` to receive those callbacks itself, as the gallery's `SeekBar` does.

## Known gaps

- Linux keeps presses, hovers and wheels from a page or a video's controls where the app does not show them, as NSH does; drags that begin there are not followed.
